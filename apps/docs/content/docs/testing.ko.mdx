**테스트** 탭에는 프로젝트마다 하나의 테스트 케이스 라이브러리가 있습니다. 케이스는 문서가 아니라 구조화된 기록입니다. 단계가 타입이 있는 목록이므로 사람과 에이전트가 같은 케이스를 같은 방식으로 실행합니다.

## 케이스의 구조

각 케이스는 `TC-<n>` 키, 그룹화를 위한 모듈, 사전 조건, 순서가 있는 단계(각 단계마다 동작과 확인 가능한 기대 결과), 그리고 유형을 가집니다. 유형은 보기보다 중요합니다. `business_flow`, `permission`, `data_consistency`가 있는 이유는 라이브러리가 코드 수준 확인만으로 조용히 퇴화하지 않게 하기 위해서입니다.

모든 단계에 동작과 기대 결과가 있는 케이스만 **활성**이 될 수 있습니다. 확인할 기대 결과가 없으면 실행 결과는 "통과"일 수밖에 없으므로, 확인할 단계가 없는 케이스는 `draft`로 만들어지고, 단계를 갖추는 저장에서 활성이 됩니다. 그 밖의 초안은 승인을 기다립니다: 일부러 초안으로 만든 것, 단계가 원래 갖춰져 있던 것, 에이전트가 단계를 써 넣은 것입니다.

에이전트가 쓴 케이스는 생성 작업에서든 CLI에서든 `draft`로 들어가고 사람이 승인합니다. 에이전트는 케이스를 승인하거나 활성으로 만들 수 없고, 활성 케이스가 태스크나 테스트 포인트를 검증한다고 주장할 수도 없으며(과거 통과가 바로 계산되기 때문), 활성 케이스를 커버리지나 회귀에서 뺄 수도 없습니다(상태 변경, 삭제, 연결 해제, 검증하는 테스트 포인트 폐기, 계획에서 제외, 회귀 autopilot의 계획 변경·일시 중지·일정 변경 모두 불가). 폐기된 케이스의 상태도 사람이 정합니다. 실패하는 케이스야말로 라운드가 찾아내야 할 신호이며, 그것을 내릴지는 사람이 정합니다. 에이전트는 아무도 승인하지 않은 AI 초안만 삭제할 수 있고, 그 편집은 케이스 이력에 에이전트 편집으로 남습니다.

케이스는 **어떤 저장소와 관련되는지**도 기록합니다. 프로젝트는 여러 저장소를 연결할 수 있고, 케이스는 역할로 관련 저장소를 지정합니다.

| 역할 | 의미 |
| --- | --- |
| `under_test` | 동작을 검증할 대상 시스템 |
| `driver` | 케이스가 동작을 수행하는 곳 |
| `verifier` | 케이스가 결과를 관찰하는 곳 |
| `fixture` | 케이스가 데이터를 준비하는 곳 |

시스템을 넘나드는 경우 `scope`를 `cross_repo`로 설정합니다. 관리자 백엔드에서 가격을 변경하고 모바일 앱에서 확인하는 식입니다. 이런 케이스에는 역할이 다른 저장소가 최소 두 개 필요하며, 그렇지 않으면 서버가 거부합니다. 역할이 하나뿐인 "크로스 저장소" 케이스는 상관지을 대상이 없기 때문입니다.

## 테스트 포인트: 커버리지를 무엇으로 셀까

케이스를 태스크에 연결하는 것만으로는 요구사항의 어떤 조건을 확인하는지 알 수 없습니다. 예전에는 정상 경로 케이스 하나만 통과해도 태스크가 검증됨으로 표시되었고, 거부·경계값·권한에는 케이스가 하나도 없을 수 있었습니다.

그래서 태스크를 **테스트 포인트**(`TP-1`, `TP-2` …)로 나눌 수 있습니다. 각각 단독으로 옳고 그름을 판정할 수 있는 조건입니다(예: "잔액을 초과하는 주문은 메시지와 함께 거부된다"). 테스트 포인트에는 유형(정상 경로·예외·경계값·권한·상태·데이터 정합성·비기능)이 있고, 케이스는 어떤 포인트를 검증하는지 선언합니다. 활성 케이스가 검증하지 않는 포인트는 **미커버**, 승인할 수 있는 초안만 검증하는 포인트는 **초안만**(남은 일은 초안 승인), 커버하는 활성 케이스 중 하나라도 실패하면 **실패**, 커버하는 활성 케이스가 모두 통과해야 **통과**입니다. 생성 작업은 경계값이나 거부되는 역할마다 케이스를 하나씩 쓰므로, 그중 하나의 통과는 나머지에 대해 아무것도 말해 주지 않습니다.

세는 것은 각 케이스의 현재 판정입니다: 활성 케이스로서 지금의 단계로 실행한 라운드에 기록된 최신 `passed` 또는 `failed`. `blocked`와 `skipped`는 실행되지 않았다는 뜻이므로 이전 실패를 지우지 않습니다. 케이스가 확인하는 내용(단계, 사전 조건, 전체 기대 결과, 테스트 데이터)을 바꾸거나 시험 실행한 초안을 승인하면 다시 실행해야 셉니다.

테스트 포인트가 있는 태스크는 모든 활성 포인트가 커버되고 통과했으며 활성 케이스에 실패가 없을 때만 **검증됨**입니다. 포인트가 없는 태스크는 연결된 케이스로 판단하고 **검증됨** 대신 **케이스 통과**로 표시합니다. 무엇을 확인해야 하는지 아무도 정하지 않았기 때문입니다. 초안과 폐기된 케이스는 세지 않습니다.

**테스트 → 커버리지**는 프로젝트에서 취소되지 않은 모든 태스크를 나쁜 순서로 보여줍니다: 실패, 테스트 없음, 미커버 포인트 있음, 초안만 커버하는 포인트 있음(검토 대기), 테스트 포인트 없음, 모두 통과하지 않음, 검증됨. 릴리스 전에 이 목록을 차례로 처리합니다.

## 에이전트로 케이스 생성하기

테스트 페이지에서 **AI로 생성**을 누릅니다. 생성 작업이 만들어지고 그 **범위**가 검토용으로 열립니다. 이 시점에는 아직 아무것도 시작되지 않았습니다.

범위는 프로젝트 자체의 리소스에서 구성됩니다. 연결된 각 저장소가 읽기 대상이 되고, 각 `document` 리소스가 업무 지식 참조가 됩니다. 승인하기 전에 경로 글롭, 대상 태스크, 대상 모듈로 좁히세요.

<Callout type="warn">
승인은 게이트이며 우회할 방법이 없습니다. 범위가 잘못된 실행은 누군가 알아차리기 전에 컨텍스트 윈도우를 통째로 소모합니다.
</Callout>

승인 후 작업을 에이전트에 디스패치합니다. 에이전트는 먼저 기존 케이스 요약을 가져오므로, 두 번째 실행부터는 기존 것을 다시 나열하는 대신 **증분**을 만들어냅니다. 각 항목은 다음 세 종류 중 하나로 분류됩니다.

- **new** — 아직 아무것도 다루지 않은 동작. `draft`로 라이브러리에 들어가 검토를 기다립니다.
- **update** — 기존 케이스가 이제 부정확하거나 불완전한 경우. 대상이 아직 draft이면 그 자리에서 수정되고, 이미 승인되었다면 **제안**이 되어 현재 값과 나란히 놓고 채택하거나 거절합니다.
- **obsolete** — 더 이상 존재하지 않는 동작.

승인된 케이스가 조용히 덮어써지는 일은 없습니다. 그것이 검토의 의미입니다.

케이스를 쓰기 전에 에이전트는 범위 안의 각 태스크를 테스트 포인트로 나누고(기존 것을 읽고 유형별로 빠진 것을 추가), 포인트마다 케이스를 도출합니다. 입력에는 동치 클래스와 경계값, 권한에는 거부되는 모든 역할, 상태에는 모든 잘못된 전이. 각 케이스는 검증하는 포인트를 선언하며, 사람이 쓴 포인트를 에이전트가 고쳐 쓰지 않습니다. 작업이 끝나면 아직 어떤 케이스도 커버하지 않는 포인트가 작업 페이지에 표시됩니다.

## 에이전트에게 업무를 이해시키기

생성되는 케이스의 품질은 에이전트가 무엇을 아는지에 달려 있습니다. 코드는 시스템이 무엇을 하는지 알려주지만, 업무가 무엇을 요구하는지는 알려주지 않습니다. 그것을 채우는 경로가 셋 있으며, 모두 코드가 필요 없습니다.

1. **워크스페이스 스킬.** `qa-domain-knowledge` 같은 이름으로 스킬을 만들고 `references/billing-rules.md`, `references/permission-matrix.md`, `references/entity-lifecycle.md`를 넣어 QA 에이전트에 연결합니다. 스킬의 `description`은 명시적인 트리거 문장으로 쓰세요. 모델이 그 파일을 여는지 여부는 이 설명만으로 결정됩니다.
2. **워크스페이스 컨텍스트.** 설정 → 워크스페이스 → 컨텍스트. 워크스페이스의 모든 태스크에 전달되므로, 항상 참인 스무 줄 남짓의 규칙만 담으세요.
3. **`document` 프로젝트 리소스.** PRD나 API 명세를 URL로 첨부하면 지속적인 프로젝트 컨텍스트가 되고, 에이전트는 케이스를 제안하기 전에 읽도록 지시받습니다. [프로젝트 리소스](/docs/project-resources)를 참고하세요.

## 테스트 계획과 실행 라운드

**테스트 계획**은 반복 가능한 케이스 집합을 선택합니다. **라운드**는 계획(또는 즉석에서 고른 케이스들)을 한 번 실행하는 것입니다.

라운드가 시작될 때 각 케이스의 스냅샷이 고정됩니다. 이후 케이스를 편집해도 그 라운드가 실제로 실행한 내용은 바뀌지 않습니다. 그렇지 않으면 회귀 이력이 스스로 다시 쓰이게 됩니다.

각 케이스를 `passed`, `failed`, `blocked`, `skipped`로 기록합니다. `blocked`는 애초에 실행할 수 없었다는 뜻이지 `failed`의 완곡한 표현이 아닙니다. 그렇게 쓰면 회귀를 숨기게 됩니다. 실패한 케이스에서는 스냅샷과 라운드 링크를 담은 결함 태스크를 한 번에 만들 수 있습니다.

**재실행은 새 라운드를 만들며**, 원래 라운드를 가리킵니다. 원래 라운드는 초기화되지 않습니다. 전체, 실패한 것만, 또는 선택한 것만 재실행할 수 있습니다.

각 케이스의 상세 페이지에는 그 케이스가 등장한 모든 라운드의 결과와 각 라운드로 가는 링크가 표시됩니다. 이 타임라인이야말로 케이스 라이브러리를 유지할 가치입니다.

계획에는 **규칙**도 둘 수 있습니다: 모듈, 우선순위, 케이스 유형, 따라갈 태스크, 또는 프로젝트의 모든 활성 케이스. 라운드는 계획에 나열된 케이스를 실행한 뒤 그 시점에 규칙과 일치하는 활성 케이스를 실행하므로, 계획을 만든 뒤에 작성된 케이스도 회귀에서 빠지지 않습니다. 폐기된 케이스는 건너뜁니다.

라운드를 직접 실행할 때 케이스를 펼치면 고정된 단계가 보입니다. 단계마다 결과와 실제로 본 것을 기록하고 **증거 추가**로 스크린샷이나 로그를 첨부합니다. 단계 결과는 케이스 결과와 함께 저장되고 에이전트와 같은 규칙으로 검증됩니다. 실패한 단계가 있는 케이스는 통과로 기록할 수 없습니다.

## 에이전트에게 라운드를 실행시키기

라운드를 에이전트에 디스패치하면, 고정된 스냅샷을 실행하며 진행하는 대로 CLI로 결과를 기록합니다.

큐에 넣기 전에 서버는 그 라운드에 필요한 **케이퍼빌리티**(단말, 데스크톱, 브라우저)를 각 daemon이 보고한 실체와 대조합니다. 제공할 수 있는 것이 없으면 라운드는 부족한 종류를 명시하며 `blocked`가 됩니다. 디스패치하고 몇 분 뒤에야 기기가 없다는 것을 발견하는 일을 피하기 위해서입니다. 해석 결과는 라운드에 고정되어 같은 라운드의 케이스는 모두 같은 기기에서 실행됩니다. 재실행은 새 라운드이며 디스패치할 때 다시 해석됩니다.

에이전트는 그 라운드에 연결된 것만 조작할 수 있습니다. 호스트에서 `adb`, 시뮬레이터, 브라우저를 찾는 일은 명시적으로 금지되어 있습니다. 연결되지 않은 것은 조작해서는 안 됩니다.

<Callout>
브라우저는 런타임의 `playwright` 또는 `chrome-devtools` MCP 서버로, Android 휴대폰은 테스트 호스트의 Artemis로, iPhone은 테스트 호스트의 디바이스 허브로 실행합니다. computer-use는 아직 구현되지 않았습니다. 필요한 케이퍼빌리티를 어떤 런타임도 제공하지 못하는 라운드는 빠진 종류를 밝히고 `blocked`로 보류되며, 기기 없이 실행되지 않습니다.
</Callout>

에이전트의 `passed` 또는 `failed`는 스냅샷의 **모든** 단계에 결과가 있고 그 케이스에 증거가 하나 이상 이미 업로드되어 있을 때만 받아들여집니다. 그래서 증거를 먼저 올리고 판정을 나중에 기록합니다. 모든 단계에 결과가 있는 통과에는 통과한 단계도 하나 이상 있어야 하며, 어떤 단계도 실행하지 않은 케이스는 `skipped`입니다. 에이전트가 아무것도 기록하지 않고 끝나면, 마무리 요약의 `passed`는 `blocked`로 기록됩니다. 통과에는 요약에 없는 증거가 필요하기 때문입니다.

각 케이스는 에이전트의 개별 실행이 맡으며, 그 실행은 자기 케이스에만 결과를 기록하고 증거를 올릴 수 있습니다. 단계 결과 없이 보낸 판정은 이미 기록된 단계 결과와 일치해야 합니다. 라운드가 아직 진행 중일 때(실행 중이거나 수동 실행을 위해 `blocked`로 보류 중) 기록한 판정은 기록한 시점부터 셉니다. 끝난 라운드의 결과를 정정해도 관찰 시각은 유지되므로, 오래된 라운드의 정정이 그 뒤에 실행된 라운드를 덮지 않습니다. 새로운 관찰은 재실행에 기록합니다.

## CLI

어떤 에이전트든 라이브러리를 읽을 수 있지만, 라운드의 결과를 쓸 수 있는 것은 그 라운드를 실행하는 에이전트뿐이며, 케이스별로 실행하는 라운드에서는 각 실행이 자기 케이스만 씁니다.

```bash
multica testcase list --project <id> --digest --output json
multica testcase get TC-42 --output json
multica testcase proposal list --case TC-42
multica testcase point list --issue MUL-12
multica testcase point add --issue MUL-12 --title "…" --category negative
multica testcase cover TC-42 MUL-12/TP-3

multica test run get <run-id> --output json
multica test capability list --run <run-id> --output json
multica test evidence add <run-case-id> --file ./shot.png --kind screenshot
multica test result set <run-case-id> --result failed --step 1=passed --step "2=failed:실제로 본 것"
multica test defect open <run-case-id> --title "…"
```

전체 명령은 [CLI 레퍼런스](/docs/cli)를 참고하세요.
