**测试** tab 下，每个项目有一份用例库。用例是结构化记录而不是文档：步骤是带类型的列表，所以人和智能体执行的是同一件事。

## 用例的形态

每条用例有 `TC-<n>` 编号、用于分组的模块、前置条件、有序步骤（每步一个操作和一条可核对的预期），以及类型。类型比看上去重要：`business_flow`、`permission`、`data_consistency` 的存在，是为了让用例库不至于悄悄退化成只测代码。

只有每一步都有操作和预期的用例才能是**有效**用例。没有可核对的预期，执行结果只可能是“通过”，所以没有可核对步骤的用例创建为 `draft`，你补齐步骤的那次保存会让它生效。其余草稿都要审批：特意建成草稿的、步骤本来就完整的、智能体写过步骤的。

智能体写的用例——无论来自生成任务还是 CLI——都以 `draft` 落库，由人审批。智能体不能审批用例、不能把用例设为有效，也不能把有效用例移出覆盖或回归——改它的状态、删除它、解除它的关联、废弃它验证的测试点、把它移出计划都不行：失败的用例正是轮次要发现的信号，下线它由人决定。智能体只能删除智能体写的草稿，它的修改在用例历史里标为智能体修改。

用例还记录**它涉及哪几个仓库**。一个项目可以绑定多个仓库，用例按角色指明相关的那些：

| 角色 | 含义 |
| --- | --- |
| `under_test` | 被检验行为的系统 |
| `driver` | 用例在哪里执行操作 |
| `verifier` | 用例在哪里观察结果 |
| `fixture` | 用例在哪里准备数据 |

跨系统的场景把 `scope` 设为 `cross_repo` —— 在后台改价，在移动端验证。这类用例至少需要两个角色不同的仓库，否则服务端会拒绝：只有一个角色的"跨仓库"用例没有任何东西可关联。

## 测试点：覆盖率按什么算

用例关联到任务，只说明它和这条需求有关，说不出它验证了需求的哪一条条件——过去一条正常路径用例通过，任务就显示已验证，而拒绝路径、边界、权限可能一条用例都没有。

所以一个任务可以拆成若干**测试点**（`TP-1`、`TP-2`……）：每个都是能单独判定对错的条件，比如“余额不足时下单被拒并提示”。测试点有类别——正常路径、异常、边界、权限、状态、数据一致性、非功能——用例声明自己验证哪些测试点。没有有效用例验证时，测试点是**未覆盖**；只有可审批的草稿验证时是**仅草稿覆盖**，剩下的就是审批草稿；覆盖它的有效用例有一条失败，是**失败**；覆盖它的每条有效用例都通过，才是**通过**——生成任务会为每个边界值、每个被拒角色各写一条用例，其中一条通过说明不了其余的。

计算时看每条用例的当前结论：最近一次以有效用例、按现在的步骤执行的轮次里记下的 `passed` 或 `failed`。`blocked` 和 `skipped` 表示没执行，不会抹掉之前的失败。改了用例的步骤，或审批了试跑过的草稿，都要重新执行一次才算数。

有测试点的任务，只有每个有效测试点都已覆盖并通过、且它的有效用例没有失败时才算**已验证**。没有测试点的任务退回按关联用例判断，显示**用例通过**而不是**已验证**：没人列出必须验证什么。草稿和已废弃用例从不计入。

**测试 → 覆盖**按从坏到好列出项目内所有未取消的任务：失败、没有任何测试、有未覆盖的测试点、有只被草稿覆盖的测试点（待审核）、没有测试点、未全部通过、已验证。发版前按这张表逐条处理。

## 用智能体生成用例

在测试页点**AI 生成用例**。这会创建一个生成任务并打开它的**覆盖范围**供你确认 —— 此时还没有开始跑。

范围由项目自身的资源推导：每个绑定的仓库成为可读代码，每个 `document` 资源成为业务知识引用。批准前先收窄它 —— 路径范围、指定任务、指定模块。

<Callout type="warn">
审批是硬闸门，没有绕过的开关。范围错了的一次生成，会在任何人发现之前烧掉整个上下文窗口。
</Callout>

批准后把任务派给智能体。智能体会先拉取已有用例的摘要，所以第二次生成产出的是**增量**，而不是把已有的再列一遍。它把每一项归为三类之一：

- **new** —— 尚无用例覆盖的行为。以 `draft` 落入用例库等你审查。
- **update** —— 已有用例现在不准确或不完整。目标若仍是草稿则就地细化；若已定稿，则变成一条**建议**，你在原值旁边对照后决定采纳或拒绝。
- **obsolete** —— 已不存在的行为。

已定稿的用例永远不会被静默改写。这正是审查的意义。

写用例之前，智能体先把范围内的每个任务拆成测试点——先读已有的，再按类别补缺——然后逐点派生用例：有输入的覆盖等价类和边界值，权限点覆盖每个被拒角色，状态点覆盖每个非法转换。每条用例都声明它验证的测试点，人写的测试点不会被智能体改写。生成结束后，生成任务页会列出还没有用例覆盖的测试点。

## 让智能体理解你的业务

生成的用例，上限取决于智能体知道什么。代码只说明系统做了什么，不说明业务要求什么。三条通道负责补上这一层，都不需要写代码：

1. **工作区技能。** 建一个类似 `qa-domain-knowledge` 的技能，放 `references/billing-rules.md`、`references/permission-matrix.md`、`references/entity-lifecycle.md`，挂到 QA 智能体上。技能的 `description` 要写成明确的触发句 —— 模型是否会打开这些文件，只由这句描述决定。
2. **工作区上下文。** 设置 → 工作区 → 上下文。它会进入工作区的每个任务，所以只放那二十来条永远成立的规则。
3. **`document` 项目资源。** 用 URL 挂上 PRD 或接口文档，它就成为持久的项目上下文，并且智能体被要求在提出用例前先阅读。见[项目资源](/docs/project-resources)。

## 计划与轮次

**测试计划**把用例挑成一个可重复的集合。**轮次**是对一个计划（或临时勾选的一批用例）的一次执行。

轮次开始时会为每条用例冻结快照。之后再改用例，不会改变那一轮实际执行过什么 —— 否则回归历史会自己悄悄改写。

逐条记录 `passed`、`failed`、`blocked` 或 `skipped`。`blocked` 表示你根本没能执行它，它不是 `failed` 的委婉说法；那样用会把回归问题藏起来。失败的用例可一键创建缺陷任务，任务里带着快照和回到该轮次的链接。

**重跑是新建一个轮次**，指回它来自的那一轮。原轮次不会被重置。可以全部重跑、只重跑失败项，或重跑选中项。

每条用例的详情页会显示它在历次轮次中的结果，并链接回每一轮。这条时间线正是用例库值得维护的理由。

计划还可以带一条**规则**：模块、优先级、用例类型、要跟随的任务，或项目内所有有效用例。一轮会先执行计划列出的用例，再执行规则此刻匹配到的有效用例，所以计划建好之后新写的用例不会被落下。已废弃的用例会被跳过。

人工执行时，展开一条用例就能看到冻结的步骤：逐步记录结论和实际看到的情况，用**添加证据**上传截图或日志。步骤结果随用例结论一起保存，并按与智能体相同的规则校验——有失败的步骤，用例就不能记为通过。

## 让智能体执行轮次

把轮次派给智能体，它会按冻结的快照执行，边执行边通过 CLI 记录结果。

在入队之前，服务端会先把这一轮需要的**能力**（手机、桌面、浏览器）与各 daemon 上报的实际能力做解析。若无人能承接，轮次直接落 `blocked` 并写明缺哪一类，而不是派出去几分钟后才发现没有设备。解析结果会冻结到轮次上，重跑时复现同一环境。

智能体只能驱动绑定给该轮次的东西。提示词明确禁止它在宿主机上找 `adb`、模拟器或浏览器：没有绑定的，就不许驱动。

<Callout>
浏览器通过运行时上的 `playwright` 或 `chrome-devtools` MCP 服务器执行，Android 手机通过测试机上的 Artemis 执行，iPhone 通过测试机上的设备中枢执行。computer-use 尚未实现。没有任何运行时能提供所需能力的轮次会停放为 `blocked` 并写明缺的是哪一类，而不是在没有设备的情况下运行。
</Callout>

智能体记 `passed` 或 `failed` 时，必须给出快照里**每一步**的结论，并且这条用例已经至少上传过一份证据——所以它先传证据、再记结论。通过还要求至少有一步通过；一步都没执行的用例记为 `skipped`。智能体结束时什么都没记录的话，收尾摘要里的 `passed` 会记为 `blocked`：通过需要摘要里没有的证据。

每个用例由智能体的一次单独执行负责，这次执行只能为自己的用例记录结果、上传证据。不带步骤结论的用例结论必须与已记录的步骤结论一致。修正已结束轮次的结果时保留用例的执行时间，所以修正旧轮次永远不会成为该用例的最新结果；先记为 `blocked` 或 `skipped`、后来才执行的用例，从那次执行起算。

## CLI

任何智能体都能读取用例库；只有执行该轮次的智能体能写结果，按用例执行的轮次里，每次智能体执行只能写自己的用例。

```bash
multica testcase list --project <id> --digest --output json
multica testcase get TC-42 --output json
multica testcase proposal list --case TC-42
multica testcase point list --issue MUL-12
multica testcase point add --issue MUL-12 --title "…" --category negative
multica testcase cover TC-42 MUL-12/TP-3

multica test run get <run-id> --output json
multica test capability list --run <run-id> --output json
multica test evidence add <run-case-id> --file ./shot.png --kind screenshot
multica test result set <run-case-id> --result failed --step 1=passed --step "2=failed:实际看到的"
multica test defect open <run-case-id> --title "…"
```

完整命令见 [CLI 参考](/docs/cli)。
