The **Tests** tab holds one library of test cases per project. A case is a structured record, not a document: its steps are a typed list, so a person and an agent can execute the same case the same way.

## The shape of a case

Each case carries a `TC-<n>` key, a module for grouping, preconditions, an ordered list of steps (each with an action and a checkable expectation), and a type. The type matters more than it looks: `business_flow`, `permission` and `data_consistency` exist so a library does not silently collapse into code-level checks.

A case is only **active** when every step has an action and an expected result. Without them an execution can only ever come back "passed", so a case written without checkable steps starts as a `draft`, and your save that gives it checkable steps makes it active. Any other draft waits for approval: one created as a draft on purpose, one whose steps were already checkable, and one an agent wrote steps into.

A case an agent writes — in a generation job or from the CLI — starts as a `draft` that a person approves. An agent cannot approve a case or make one active, cannot claim that an active case covers an issue or test point (its past passes would count at once), and cannot take an active one out of coverage or regression — by changing its status, deleting it, unlinking it, dropping a test point it verifies, removing it from a plan, or retargeting, pausing or rescheduling a regression autopilot: a failing case is the signal a round exists to produce, and retiring it is a person's call. A deprecated case's status is a person's too. An agent may delete only AI-written drafts nobody approved, and its edits show as agent edits in the case's history.

A case also records **which repositories it touches**. A project can bind several, and a case names the ones it relates to by role:

| Role | Meaning |
| --- | --- |
| `under_test` | The system whose behaviour the case is checking |
| `driver` | Where the case performs its actions |
| `verifier` | Where the case observes the result |
| `fixture` | Where the case prepares data |

Set `scope` to `cross_repo` when a case spans systems — change a price in the admin backend, verify it in the mobile app. Such a case needs at least two repositories with different roles; the server rejects it otherwise, because a single-role "cross-repo" case has nothing to correlate.

## Test points: what coverage is counted against

Linking a case to an issue says it is about that requirement. It does not say which of the requirement's conditions it checks — and one passing happy-path case used to be enough to mark an issue verified while its refusals, limits and permissions had no case at all.

So an issue can be split into **test points** (`TP-1`, `TP-2`, …): conditions that can each be judged right or wrong on their own, such as "an order over the balance is refused with a message". Each point has a category — positive, negative, boundary, permission, state, data, non-functional — and cases declare which points they verify. A point is **uncovered** while no active case verifies it, **drafts only** while only drafts that could be approved do — approving one is what is left — **failing** when an active covering case fails, and **passed** when an active covering case passes and none is failing.

What counts is each case's current verdict: its newest `passed` or `failed` result from a round that ran it as an active case. `blocked` and `skipped` mean the case did not run, so they never clear a failure, and approving a draft that was trial-run means it has to run again before it counts.

An issue with test points is **verified** only when every active point is covered and passed and none of its active cases is failing. An issue without points falls back to its linked cases and shows **Cases pass** instead of **Verified**: nobody listed what had to be checked. Drafts and deprecated cases never count.

**Tests → Coverage** lists every live issue of a project, worst first: failing, no tests at all, uncovered points, points only drafts cover (awaiting review), no test points, not all passed, verified. It is the list to work down before a release.

## Generating cases with an agent

Press **Generate with AI** on the Tests page. This creates a generation job and opens its **scope** for review — it does not start anything yet.

The scope is seeded from the project's own resources: every bound repository becomes readable, every `document` resource becomes a business-knowledge reference. Narrow it before approving — path globs, specific issues, specific modules.

<Callout type="warn">
Approval is the gate, and there is no way around it. A run that starts with the wrong scope burns a whole context window before anyone notices.
</Callout>

Once approved, dispatch the job to an agent. The agent pulls the existing-case digest first, so a second run produces an **increment** rather than re-emitting what you already have. It classifies every item as one of three kinds:

- **new** — behaviour nothing covers yet. Lands in the library as a `draft` for you to review.
- **update** — an existing case that is now wrong or incomplete. If the target is still a draft it is refined in place; if it has already been approved, it becomes a **proposal** you accept or reject side by side with the current value.
- **obsolete** — behaviour that no longer exists.

An approved case is never rewritten silently. That is the whole point of review.

Before writing cases, the agent splits every issue in scope into test points — reading the ones that exist and adding what is missing, category by category — and derives cases point by point: equivalence classes and boundary values for inputs, every refused role for permissions, every illegal transition for states. Each case names the points it verifies, and a point a person wrote is never rewritten by an agent. When the job ends, its page lists the points no case covers yet.

## Teaching an agent your business

Generated cases are only as good as what the agent knows. Code tells it what the system does; it does not tell it what the business requires. Three channels feed that in, none of which need code:

1. **A workspace skill.** Create one named something like `qa-domain-knowledge` with `references/billing-rules.md`, `references/permission-matrix.md`, `references/entity-lifecycle.md`, and attach it to your QA agent. Write the skill's `description` as an explicit trigger sentence — that description is the only thing that decides whether the model opens the files.
2. **Workspace context.** Settings → Workspace → Context. It reaches every task in the workspace, so keep it to the twenty or so rules that are always true.
3. **`document` project resources.** Attach a PRD or an API spec by URL and it becomes durable project context the agent is told to read before proposing cases. See [Project resources](/docs/project-resources).

## Plans and runs

A **test plan** picks cases into a repeatable set. A **run** executes a plan (or an ad-hoc selection) once.

When a run starts it freezes each case as a snapshot. Editing the case afterwards does not change what that round executed — otherwise the regression history would quietly rewrite itself.

Record each case as `passed`, `failed`, `blocked` or `skipped`. `blocked` means you could not run it at all; it is not a softer word for `failed`, and using it that way hides regressions. A failing case opens a defect issue carrying the snapshot and a link back to the round.

**Retrying creates a new run**, pointing back at the one it came from. The original is never reset. Retry everything, only the failures, or a selection.

Each case's detail page shows its result across every round it appeared in, with a link back to each one. That timeline is the reason a case library is worth maintaining.

A plan can also carry a **rule** — modules, priorities, case types, issues whose cases to follow, or every active case of the project. A round of the plan runs its listed cases and then every active case the rule matches at that moment, so cases written after the plan was built are not left out of its regression. Deprecated cases are skipped.

When you execute a round by hand, expand a case to see its frozen steps: record each step's result and what you observed, and attach screenshots or logs with **Add evidence**. The step results are saved with the case's result and checked the same way as an agent's — a case cannot pass while one of its steps failed.

## Letting an agent execute a run

Dispatch a run to an agent and it executes the frozen snapshots, recording results through the CLI as it goes.

Before anything is queued, the server resolves the **capabilities** the run needs — a phone, a desktop, a browser — against what your daemons report. If nothing can serve the run it is parked as `blocked` with the missing kind named, rather than dispatched to discover minutes later that there is no device. The resolution is frozen onto the round, so every case of it runs against the same devices; a retry is a new round and resolves again when it is dispatched.

The agent may only drive what was bound to the run. It is told never to go looking for an `adb`, a simulator or a browser on the host: if it was not bound, it may not be driven.

<Callout>
Browsers run through a `playwright` or `chrome-devtools` MCP server on the runtime, Android phones through Artemis on a test host, and iPhones through the device hub on a test host. Computer-use is not implemented yet. A round whose capability no runtime provides is parked as `blocked` with the missing kind named, rather than running without a device.
</Callout>

An agent's `passed` or `failed` is only accepted with a result for **every** step of the snapshot and at least one evidence file already uploaded for that case, so it uploads evidence first and records the verdict second. If an agent finishes without recording anything, a `passed` in its closing summary is recorded as `blocked`: a pass needs the evidence the summary does not carry.

Each case is executed by its own agent run, which can record a result or upload evidence for that case only. A verdict sent without step results has to agree with the step results already recorded. A verdict recorded while its round is still open — running, or parked as `blocked` for hand execution — counts from when it was recorded. Correcting the result of a finished round keeps the time it was observed, so a fix to an old round never outranks a round that ran since; a new observation belongs in a retry.

## CLI

Any agent can read the library; only the agent executing a round can write its results, and in a round executed case by case each agent run writes only its own case.

```bash
multica testcase list --project <id> --digest --output json
multica testcase get TC-42 --output json
multica testcase proposal list --case TC-42
multica testcase point list --issue MUL-12
multica testcase point add --issue MUL-12 --title "…" --category negative
multica testcase cover TC-42 MUL-12/TP-3

multica test run get <run-id> --output json
multica test capability list --run <run-id> --output json
multica test evidence add <run-case-id> --file ./shot.png --kind screenshot
multica test result set <run-case-id> --result failed --step 1=passed --step "2=failed:what you saw"
multica test defect open <run-case-id> --title "…"
```

See [CLI reference](/docs/cli) for the full surface.
