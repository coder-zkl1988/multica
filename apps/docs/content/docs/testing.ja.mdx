**テスト** タブには、プロジェクトごとに 1 つのテストケースライブラリがあります。ケースはドキュメントではなく構造化された記録です。手順が型付きのリストなので、人とエージェントが同じケースを同じように実行できます。

## ケースの形

各ケースは `TC-<n>` のキー、グループ分け用のモジュール、事前条件、順序付きの手順（各手順に操作と検証可能な期待結果）、そして種別を持ちます。種別は見た目以上に重要です。`business_flow`、`permission`、`data_consistency` があるのは、ライブラリがコードレベルの確認だけに静かに退化しないためです。

すべての手順に操作と期待結果があるケースだけが**有効**になれます。確認できる期待結果がなければ実行結果は「合格」にしかならないため、確認できる手順のないケースは `draft` として作成され、手順をそろえた保存で有効になります。それ以外の下書きは承認を待ちます：意図して下書きとして作ったもの、手順がもともとそろっていたもの、エージェントが手順を書き込んだものです。

エージェントが書いたケースは、生成ジョブでも CLI でも `draft` として入り、人が承認します。エージェントはケースを承認することも有効にすることもできず、有効なケースをカバレッジや回帰から外すこともできません（状態の変更、削除、関連付けの解除、検証しているテストポイントの廃止、計画からの除外のいずれも不可）。失敗するケースこそラウンドが見つけるべきシグナルであり、それを外すかどうかは人が決めます。エージェントが削除できるのはエージェントが書いた下書きだけで、その編集はケースの履歴にエージェントによる編集として残ります。

ケースは **どのリポジトリに関係するか** も記録します。プロジェクトは複数のリポジトリを紐付けられ、ケースは役割で関係先を指定します。

| 役割 | 意味 |
| --- | --- |
| `under_test` | 振る舞いを検証する対象のシステム |
| `driver` | ケースが操作を行う場所 |
| `verifier` | ケースが結果を観察する場所 |
| `fixture` | ケースがデータを準備する場所 |

システムをまたぐ場合は `scope` を `cross_repo` にします。管理画面で価格を変更し、モバイルアプリで確認する、といったケースです。この種のケースには役割の異なるリポジトリが最低 2 つ必要で、そうでなければサーバーが拒否します。役割が 1 つだけの「クロスリポジトリ」ケースには相関させるものが何もないからです。

## テストポイント：カバレッジを何で数えるか

ケースをタスクにリンクしても、それが要件のどの条件を確認するのかは分かりません。以前は正常系のケースが 1 件合格するだけでタスクが検証済みになり、拒否・境界値・権限には 1 件もケースがないこともありました。

そこでタスクを**テストポイント**（`TP-1`、`TP-2`…）に分解できます。それぞれが単独で正誤を判定できる条件です（例：「残高を超える注文はメッセージ付きで拒否される」）。テストポイントには種別（正常系・異常系・境界値・権限・状態・データ整合性・非機能）があり、ケースはどのポイントを検証するかを宣言します。有効なケースが検証していないポイントは**未カバー**、承認できる下書きだけが検証しているポイントは**下書きのみ**（残るのは下書きの承認）、カバーする有効なケースのどれかが失敗していれば**失敗**、カバーする有効なケースがすべて合格して初めて**合格**です。生成ジョブは境界値や拒否されるロールごとに 1 件ずつケースを書くので、そのうち 1 件の合格はほかについて何も示しません。

数えるのは各ケースの現在の判定です：有効なケースとして、いまの手順で実行したラウンドに記録された最新の `passed` または `failed`。`blocked` と `skipped` は実行されなかったという意味なので、以前の失敗を消しません。ケースの手順を変えたとき、試し実行した下書きを承認したときは、もう一度実行するまで数えられません。

テストポイントのあるタスクは、有効なポイントがすべてカバー・合格し、有効なケースに失敗がないときだけ**検証済み**です。ポイントのないタスクはリンクされたケースで判断し、**検証済み**ではなく**ケース合格**と表示します。何を確認すべきか誰も挙げていないからです。下書きと廃止済みのケースは数えません。

**テスト → カバレッジ** は、プロジェクト内のキャンセルされていないタスクを悪い順に並べます：失敗、テストなし、未カバーのポイントあり、下書きだけがカバーするポイントあり（レビュー待ち）、テストポイントなし、未合格あり、検証済み。リリース前にこの一覧を順に片付けます。

## エージェントによるケース生成

テストページで **AI で生成** を押します。生成ジョブが作成され、その **スコープ** がレビュー用に開きます。この時点ではまだ何も始まっていません。

スコープはプロジェクト自身のリソースから組み立てられます。紐付けられた各リポジトリが読み取り対象になり、各 `document` リソースが業務知識の参照になります。承認する前に、パスグロブ・対象タスク・対象モジュールで絞り込んでください。

<Callout type="warn">
承認はゲートであり、迂回手段はありません。スコープを誤った実行は、誰かが気づく前にコンテキストウィンドウを丸ごと使い切ります。
</Callout>

承認後、ジョブをエージェントにディスパッチします。エージェントはまず既存ケースのダイジェストを取得するため、2 回目以降の実行は既存のものを並べ直すのではなく **差分** を生成します。各項目は次の 3 種のいずれかに分類されます。

- **new** — まだ何もカバーしていない振る舞い。`draft` としてライブラリに入り、レビューを待ちます。
- **update** — 既存ケースが不正確または不十分になった場合。対象がまだ draft ならその場で改訂され、承認済みなら **提案** となり、現在の値と並べて採用・却下を判断します。
- **obsolete** — もう存在しない振る舞い。

承認済みのケースが黙って書き換えられることはありません。それがレビューの意味です。

ケースを書く前に、エージェントは範囲内の各タスクをテストポイントに分解し（既存のものを読み、種別ごとに不足を追加）、ポイントごとにケースを導きます。入力には同値クラスと境界値、権限には拒否されるすべてのロール、状態にはすべての不正な遷移。各ケースは検証するポイントを宣言し、人が書いたポイントをエージェントが書き換えることはありません。ジョブが終わると、まだどのケースにもカバーされていないポイントがジョブのページに表示されます。

## エージェントに業務を理解させる

生成されるケースの質は、エージェントが何を知っているかで決まります。コードはシステムが何をするかを示しますが、業務が何を要求するかは示しません。それを補う経路が 3 つあり、いずれもコード不要です。

1. **ワークスペーススキル。** `qa-domain-knowledge` のような名前でスキルを作り、`references/billing-rules.md`、`references/permission-matrix.md`、`references/entity-lifecycle.md` を置いて QA エージェントに紐付けます。スキルの `description` は明示的なトリガー文にしてください。モデルがそのファイルを開くかどうかは、この説明だけで決まります。
2. **ワークスペースコンテキスト。** 設定 → ワークスペース → コンテキスト。ワークスペースのすべてのタスクに届くので、常に成り立つ 20 行程度のルールに留めてください。
3. **`document` プロジェクトリソース。** PRD や API 仕様を URL で添付すると、永続的なプロジェクトコンテキストになり、エージェントはケースを提案する前に読むよう指示されます。[プロジェクトリソース](/docs/project-resources)を参照してください。

## テスト計画と実行ラウンド

**テスト計画** は再利用できるケースの集合を選びます。**ラウンド** は計画（またはその場で選んだケース群）を 1 回実行するものです。

ラウンド開始時に各ケースのスナップショットが凍結されます。その後にケースを編集しても、そのラウンドが実際に実行した内容は変わりません。そうでなければ回帰履歴が勝手に書き換わってしまいます。

各ケースを `passed`、`failed`、`blocked`、`skipped` で記録します。`blocked` は「そもそも実行できなかった」という意味であり、`failed` の柔らかい言い換えではありません。そう使うと回帰を隠すことになります。失敗したケースからは、スナップショットとラウンドへのリンクを含む欠陥タスクをワンクリックで作成できます。

**再実行は新しいラウンドを作成し**、元のラウンドを指し示します。元のラウンドがリセットされることはありません。全件・失敗のみ・選択分のいずれかを再実行できます。

各ケースの詳細ページには、そのケースが登場したすべてのラウンドでの結果と、各ラウンドへのリンクが表示されます。このタイムラインこそ、ケースライブラリを維持する価値です。

計画には**ルール**も設定できます：モジュール、優先度、ケース種別、追跡するタスク、またはプロジェクト内のすべての有効なケース。ラウンドは計画に並んだケースを実行したあと、その時点でルールに一致する有効なケースを実行するので、計画作成後に書かれたケースも回帰から漏れません。廃止済みのケースはスキップされます。

ラウンドを手作業で実行するときは、ケースを展開すると凍結された手順が見えます。手順ごとに結果と実際に見えたことを記録し、**証跡を追加** でスクリーンショットやログを添付します。手順の結果はケースの結果と一緒に保存され、エージェントと同じ規則で検証されます。失敗した手順があるケースは合格にできません。

## エージェントにラウンドを実行させる

ラウンドをエージェントにディスパッチすると、凍結されたスナップショットを実行し、進めながら CLI で結果を記録します。

キューに入れる前に、サーバーはそのラウンドが必要とする **ケイパビリティ**（端末・デスクトップ・ブラウザ）を、各 daemon が報告している実体と突き合わせます。提供できるものがなければ、ラウンドは不足している種別を明示して `blocked` になります。ディスパッチしてから数分後に端末がないと判明する、ということを避けるためです。解決結果はラウンドに凍結され、再実行時に同じ環境が再現されます。

エージェントはそのラウンドに紐付けられたものしか操作できません。ホスト上で `adb`・シミュレータ・ブラウザを探すことは明示的に禁止されています。紐付けられていないものは操作してはいけません。

<Callout>
ブラウザはランタイムの `playwright` または `chrome-devtools` MCP サーバーで、Android 端末はテストホスト上の Artemis で、iPhone はテストホスト上のデバイスハブで実行します。computer-use はまだ実装されていません。必要なケイパビリティをどのランタイムも提供できないラウンドは、足りない種類を明記して `blocked` で保留され、端末なしで実行されることはありません。
</Callout>

エージェントの `passed` / `failed` は、スナップショットの**すべての**手順の結果があり、そのケースに少なくとも 1 件の証跡がすでにアップロードされている場合にだけ受け付けられます。そのため証跡を先に、判定を後に記録します。合格には少なくとも 1 つの合格した手順も必要で、どの手順も実行しなかったケースは `skipped` です。エージェントが何も記録せずに終わった場合、締めくくりのサマリーにある `passed` は `blocked` として記録されます。合格にはサマリーにない証跡が必要だからです。

各ケースはエージェントの個別の実行が担当し、その実行が結果を記録し証跡をアップロードできるのは自分のケースだけです。手順結果を付けずに送った判定は、記録済みの手順結果と一致していなければなりません。終了したラウンドの結果を訂正しても実行時刻は保たれるため、古いラウンドの訂正がそのケースの最新結果になることはありません。最初に `blocked` や `skipped` と記録され、あとで実行されたケースはその実行から数えます。

## CLI

どのエージェントでもライブラリを読めますが、ラウンドの結果を書けるのはそのラウンドを実行するエージェントだけで、ケースごとに実行するラウンドでは各実行が自分のケースだけを書きます。

```bash
multica testcase list --project <id> --digest --output json
multica testcase get TC-42 --output json
multica testcase proposal list --case TC-42
multica testcase point list --issue MUL-12
multica testcase point add --issue MUL-12 --title "…" --category negative
multica testcase cover TC-42 MUL-12/TP-3

multica test run get <run-id> --output json
multica test capability list --run <run-id> --output json
multica test evidence add <run-case-id> --file ./shot.png --kind screenshot
multica test result set <run-case-id> --result failed --step 1=passed --step "2=failed:実際に見えたこと"
multica test defect open <run-case-id> --title "…"
```

全コマンドは [CLI リファレンス](/docs/cli) を参照してください。
