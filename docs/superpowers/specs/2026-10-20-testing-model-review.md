# 测试模型审视与整改（2026-10-20）

> 状态：`proposal`（用户 2026-10-20 授权“按你的经验进行修改”，已实现，待验收）
> 范围：测试域模型本身——用例结构、需求覆盖口径、结果记录、回归选择、AI 生成方式。执行基础设施（设备、MCP、派发、并行）不在本次范围。
> 前置阅读：`docs/product/testing-center/README.md`、`decision-register.md`、`2026-08-05-test-case-management-design.md`

## 1. 结论

测试中心的执行链路（设备、浏览器、按用例派发、证据上传）已经很完整，但**测试模型本身有三处会系统性地漏 bug**，而且这三处都会让界面显示“没问题”：

1. **覆盖率无法度量，且被高估。** 需求卡片上的“已验证”= 至少关联一条用例、且每条关联用例最近一次结果是 passed。一个有 10 个验收点的需求，只要关联了 1 条通过的用例就显示“已验证”；3 个月前旧版本上的通过，在需求改过之后仍然算数；草稿和已废弃的用例也算。系统里没有“这个需求要验证哪些点”的概念，所以“哪些点从没被测过”这个问题根本无法回答——这正是漏测最多的地方。
2. **一条“通过”可能什么都没验证。** 用例可以零步骤、步骤可以没有期望结果，照样能激活、能执行；智能体标 `passed` 不需要逐步结果、不需要证据；`step_results` 服务端不校验形状。于是“通过”既不能说明每一步都看过，也不能告诉你失败时是哪一步。
3. **回归集合会腐烂。** 计划是手工挑选的静态列表。用例库每天在长，但新用例不会进入已有的回归计划，autopilot 的夜间回归永远跑当初那一批。

另外还有一处会改写历史的缺陷：结果写入不检查轮次状态，已中止的轮次会被迟到的结果翻成“已完成”，已完成的轮次也能被智能体改写。

## 3. 整改方案

### 3.1 需求测试点（验收点）—— 覆盖率的分母

新增 `issue_test_point`：一个需求的一条可独立判定对错的验证条件（“余额不足时下单被拒并提示”）。用例通过 `test_case_test_point` 声明自己验证哪些测试点。

- 测试点挂在 Issue 下，有序编号（`TP-<n>`，每个 Issue 内从 1 起）、标题、可选说明、`category`（`positive` 正常路径 / `negative` 异常与非法输入 / `boundary` 边界 / `permission` 权限 / `state` 状态转换 / `data` 数据一致性 / `non_functional` 非功能），`origin ai|human`，`status active|dropped`。人工建的测试点不会被 AI 改写（与 TS-009 同一条线）。
- 覆盖口径：一个测试点**被覆盖** = 至少一条 `active` 用例声明验证它；**已通过** = 声明它的**每一条** `active` 用例的当前结论都是 `passed`（当前结论见 3.7：最近一次以有效用例、按现在的程序执行的 `passed` / `failed`；本节原稿写的“至少一条通过且没有失败”已被替代）。没有有效用例、只有草稿声明它的测试点是 `in_review`（仅草稿覆盖）：审批草稿就是剩下的事，与“没人写用例”的 `uncovered` 分开（复审后补充，见 3.7）。
- **“已验证”重新定义**：需求至少有一个 `active` 测试点，且每个 `active` 测试点都被覆盖并已通过。没有拆测试点的需求退回旧口径，但响应里带 `basis: "cases_only"`，界面明示“未拆验收点，仅代表关联用例通过”，不再给出与有测试点时同等强度的“已验证”。
- 只计 `active` 用例：草稿、已废弃一律不参与覆盖与验证（修 A3）。
- 需求页测试区块列出测试点：覆盖状态、通过状态、验证它的用例；未覆盖的测试点高亮——这就是“漏测清单”。

### 3.2 AI 生成改为“先拆点、再逐点设计”

- 生成提示词：先为 `plan.issues` 中的每个需求列出测试点（已有测试点先读、只补缺口），再对每个测试点按类别派生用例：正常路径至少一条；有输入的点要覆盖非法输入与边界值；有角色差异的点要覆盖无权限的角色；有状态的点要覆盖非法状态转换。每条新用例必须声明它验证的测试点。
- 删掉“宁少勿多”这句无下限的引导，改为“精确不等于少：每个测试点都要被覆盖，除非明确说明为何无法用用例验证”。
- 结果 JSON 增加 `coverage`：每个测试点是否被覆盖、由哪些用例覆盖、未覆盖的原因。
- 服务端：提议的用例用 `case.test_points` 声明它验证的测试点，只能引用本次范围内任务的测试点；AI 先用 `multica testcase point add` 新增测试点（`origin = ai`），再在提议里引用。
  - 实现时的调整：原本打算“范围内的新用例不声明测试点就拒绝”。守护进程与服务器版本可能不一致，旧守护进程的提示词不认识测试点，硬拒会让整次生成失败，因此改为不拒绝、在响应里计数（`new_cases_without_test_points`），由提示词、需求页未覆盖清单与结束时的覆盖快照承担约束。

### 3.3 用例质量门槛

- 激活（`draft → active`，以及以 `active` 状态创建 / 编辑）要求：至少一个步骤，每个步骤 `action` 与 `expected` 都非空。草稿可以不完整（草稿就是半成品）。
- 人写的用例创建时没有可执行步骤就落为草稿；补齐步骤的那次保存让它生效（保存里显式给了 `status` 则按其值）。步骤本来就完整的草稿与 AI 草稿要审批。
- 智能体写的用例走同一道审批：新建为 `origin ai` 的草稿；智能体不能审批、不能设为 `active`、不能废弃或删除 `active` 用例、不能决定提议（TS-043）。
- AI 提议的 `new` / `update` 用例必须满足同一门槛——提示词早就这么要求，现在由服务端兑现。
- 新建轮次跳过 `deprecated` 用例（计划里还列着也照跑其余用例），只有全部被跳过、什么都选不出时才拒绝建轮次；草稿可以进轮次（审查者试跑草稿是合理的），但其结果不计入覆盖与验证。

### 3.4 结果记录可信

- `step_results` 有了形状：`[{index, result: passed|failed|blocked|skipped|not_run, actual?, note?}]`，`index` 必须是快照里存在的步骤，不得重复。
- 智能体（任务 token）写入 `passed` / `failed` 时：必须给出覆盖快照全部步骤的逐步结果；`passed` 不得含 `failed` / `blocked` / `not_run` 步骤，且（逐步结果完整时）至少一步 `passed`；`failed` 必须至少一步 `failed`；且该用例至少已上传一条证据。`blocked` / `skipped` 不强制证据（环境不可用时可能拍不到图）。
- 成员（手工测试）可以不填逐步结果——强迫逐格勾选会把人推向“全选通过”，得到的反而是更假的数据；但填了就按同一形状校验。
- 轮次状态：`aborted` 的轮次拒绝写入（409）；`completed` / `blocked` 的轮次只允许成员更正，智能体写入与上传证据都 409。自动收尾是条件写：所有用例都已有结论时，把尚未 `completed` / `aborted` 的轮次（含停放为 `blocked` 的轮次）置为 `completed`；不会把 `aborted` 翻成 `completed`，并发的两个收尾也只有一个生效。
- 按用例派发的轮次里，每个任务只能写自己的 `run_case_id`（结论与证据），写兄弟用例 403。

### 3.5 动态回归计划

- `test_plan.selector`（`NOT NULL` JSONB，默认 `{}` 即无规则）：`{all_active, modules, priorities, case_types, issue_ids}`；维度之间取交、维度内取并，`all_active` 选项目内全部有效用例，模块按存储值精确匹配。从计划建轮次时，用例集合 = 手工加入的用例 ∪ 满足规则的 `active` 用例（去重，按手工顺序在前、其余按用例号）；手工列出但已删除的用例被丢弃。autopilot 的 `test_run` 模式走同一条路径，新用例自动进入夜间回归。
- 计划详情页显示规则与“当前会纳入 N 条”。

### 3.6 本次不做，记为提案

- **B3 `case_type` 拆维度**（层级 × 技法 × 质量属性）：牵涉筛选、生成、契约与历史数据迁移。3.1 / 3.2 把覆盖的观察口径从 `case_type` 移到了测试点与其类别上，B3 的危害随之大幅下降；保留为提案 TS-041，待验收后决定。
- **结果与构建绑定的“过期”判定**（A2 的完整解）：测试点 3.1 已经让“需求改了之后补点”成为显式动作；按 `build_ref` 判定通过是否过期需要先统一构建号来源（目前是自由文本），记为提案 TS-042。

### 3.7 对抗复审后的修正（2026-10-21）

实现完成后跑了一轮对抗复审（7 个维度、逐条反驳验证），确认 37 个问题。除下列已知限制外都已修正，详见决策台账 TS-036 至 TS-040 的“复审修正”与新增的 TS-043：

- 结果：按用例任务只写自己的用例；钩子兜底与轮次完成改为条件写并推送事件；更正保留首次执行时间；不带步骤的结论按已存步骤校验；无步骤快照不能被智能体记为通过；轮次页只重发改过的步骤并保留每步 `note`。
- 覆盖：新增 `in_review`；解除用例与任务的关联时清掉对应测试点声明；人改过的 AI 测试点归人；修订替换而非累加 AI 测试点声明；生成覆盖快照此前从未写入，现已写入；覆盖页截断在过滤之后计算、随任务增删刷新。
- 计划：删除用例时从计划列表移除；模块精确匹配；用例变化刷新预览。
- 用例：人写草稿补齐步骤即生效；智能体写的用例要人审（TS-043）。
- 已知限制：删除编号最大的测试点后编号会被复用；对不认识 `selector` 的旧服务器保存规则会被静默丢弃；智能体仍可直接修改有效用例的内容，包括步骤以及会影响按规则选例的模块、优先级、类型（修订历史里记为智能体修改，可追溯）；`steps_changed_at` 取事务开始时间，与同一时刻新建的轮次之间存在极窄的竞争；全部阻塞的夜间回归仍记为完成。

第二轮对抗复审（审修复本身，46 个候选、38 个确认，去重后约 30 项）和第三轮（39 个候选、36 个确认，多为低严重度）又改了这些：

- 覆盖口径：只读每条用例的**当前结论**（最近一次以有效用例、按现在步骤执行的 `passed` / `failed`），`blocked` / `skipped` 不再抹掉失败，改步骤（迁移 929 `steps_changed_at`）和草稿试跑的结果不计入；测试点要**所有**覆盖它的有效用例都通过才算通过；`in_review` 只计可审批的草稿。
- 轮次并发：按轮次行加锁，杜绝同一用例被派给两个任务、两个钩子都不收尾；中止与整轮收尾改为条件写。
- 智能体闸门（TS-043）扩到解除关联、废弃被覆盖的测试点、缩小计划；只能删除智能体写的草稿；修订历史记为智能体修改；写入在事务里锁住重读。
- 第三轮：智能体不能为有效用例声明覆盖、不能动已废弃用例的状态、不能改回归 autopilot；“程序变了”包括前置条件、整体预期和测试数据；已结束轮次的更正不改观察时间；派发绑定与开始轮次改为条件写；覆盖页在 SQL 里排除已关闭任务并线性聚合。
- 其余：用例修订只替换本次范围内的 AI 测试点声明；排队提议覆盖的点计为待审核；重跑跳过已删除用例；覆盖页过滤后再截断；轮次页步骤草稿的同步、清空与越界序号；CLI 补上 `--steps-stdin` / `--steps-file` / `--repos` 等技能里写到的参数；文档里过时的 Android / iOS 说明。
