# 测试模型审视与整改（2026-10-20）

> 状态：`proposal`（用户 2026-10-20 授权“按你的经验进行修改”，已实现，待验收）
> 范围：测试域模型本身——用例结构、需求覆盖口径、结果记录、回归选择、AI 生成方式。执行基础设施（设备、MCP、派发、并行）不在本次范围。
> 前置阅读：`docs/product/testing-center/README.md`、`decision-register.md`、`2026-08-05-test-case-management-design.md`

## 1. 结论

测试中心的执行链路（设备、浏览器、按用例派发、证据上传）已经很完整，但**测试模型本身有三处会系统性地漏 bug**，而且这三处都会让界面显示“没问题”：

1. **覆盖率无法度量，且被高估。** 需求卡片上的“已验证”= 至少关联一条用例、且每条关联用例最近一次结果是 passed。一个有 10 个验收点的需求，只要关联了 1 条通过的用例就显示“已验证”；3 个月前旧版本上的通过，在需求改过之后仍然算数；草稿和已废弃的用例也算。系统里没有“这个需求要验证哪些点”的概念，所以“哪些点从没被测过”这个问题根本无法回答——这正是漏测最多的地方。
2. **一条“通过”可能什么都没验证。** 用例可以零步骤、步骤可以没有期望结果，照样能激活、能执行；智能体标 `passed` 不需要逐步结果、不需要证据；`step_results` 服务端不校验形状。于是“通过”既不能说明每一步都看过，也不能告诉你失败时是哪一步。
3. **回归集合会腐烂。** 计划是手工挑选的静态列表。用例库每天在长，但新用例不会进入已有的回归计划，autopilot 的夜间回归永远跑当初那一批。

另外还有一处会改写历史的缺陷：结果写入不检查轮次状态，已中止的轮次会被迟到的结果翻成“已完成”，已完成的轮次也能被智能体改写。

## 3. 整改方案

### 3.1 需求测试点（验收点）—— 覆盖率的分母

新增 `issue_test_point`：一个需求的一条可独立判定对错的验证条件（“余额不足时下单被拒并提示”）。用例通过 `test_case_test_point` 声明自己验证哪些测试点。

- 测试点挂在 Issue 下，有序编号（`TP-<n>`，每个 Issue 内从 1 起）、标题、可选说明、`category`（`positive` 正常路径 / `negative` 异常与非法输入 / `boundary` 边界 / `permission` 权限 / `state` 状态转换 / `data` 数据一致性 / `non_functional` 非功能），`origin ai|human`，`status active|dropped`。人工建的测试点不会被 AI 改写（与 TS-009 同一条线）。
- 覆盖口径：一个测试点**被覆盖** = 至少一条 `active` 用例声明验证它；**已通过** = 声明它的 `active` 用例中至少一条最近一次结果为 `passed`，且没有任何一条最近一次结果为 `failed`。
- **“已验证”重新定义**：需求至少有一个 `active` 测试点，且每个 `active` 测试点都被覆盖并已通过。没有拆测试点的需求退回旧口径，但响应里带 `basis: "cases_only"`，界面明示“未拆验收点，仅代表关联用例通过”，不再给出与有测试点时同等强度的“已验证”。
- 只计 `active` 用例：草稿、已废弃一律不参与覆盖与验证（修 A3）。
- 需求页测试区块列出测试点：覆盖状态、通过状态、验证它的用例；未覆盖的测试点高亮——这就是“漏测清单”。

### 3.2 AI 生成改为“先拆点、再逐点设计”

- 生成提示词：先为 `plan.issues` 中的每个需求列出测试点（已有测试点先读、只补缺口），再对每个测试点按类别派生用例：正常路径至少一条；有输入的点要覆盖非法输入与边界值；有角色差异的点要覆盖无权限的角色；有状态的点要覆盖非法状态转换。每条新用例必须声明它验证的测试点。
- 删掉“宁少勿多”这句无下限的引导，改为“精确不等于少：每个测试点都要被覆盖，除非明确说明为何无法用用例验证”。
- 结果 JSON 增加 `coverage`：每个测试点是否被覆盖、由哪些用例覆盖、未覆盖的原因。
- 服务端：提议的 `new` 用例若关联了需求，必须至少声明一个该需求的测试点；AI 可以通过同一次提议新增测试点（`origin = ai`）。

### 3.3 用例质量门槛

- 激活（`draft → active`，以及以 `active` 状态创建 / 编辑）要求：至少一个步骤，每个步骤 `action` 与 `expected` 都非空。草稿可以不完整（草稿就是半成品）。
- AI 提议的 `new` / `update` 用例必须满足同一门槛——提示词早就这么要求，现在由服务端兑现。
- 新建轮次拒绝 `deprecated` 用例；草稿可以进轮次（审查者试跑草稿是合理的），但其结果不计入覆盖与验证。

### 3.4 结果记录可信

- `step_results` 有了形状：`[{index, result: passed|failed|blocked|skipped|not_run, actual?, note?}]`，`index` 必须是快照里存在的步骤，不得重复。
- 智能体（任务 token）写入 `passed` / `failed` 时：必须给出覆盖快照全部步骤的逐步结果；`passed` 不得含 `failed` / `blocked` 步骤；`failed` 必须至少一步 `failed`；且该用例至少已上传一条证据。`blocked` / `skipped` 不强制证据（环境不可用时可能拍不到图）。
- 成员（手工测试）可以不填逐步结果——强迫逐格勾选会把人推向“全选通过”，得到的反而是更假的数据；但填了就按同一形状校验。
- 轮次状态：`aborted` 的轮次拒绝写入（409）；`completed` 的轮次只允许成员更正，智能体写入 409；自动收尾只在轮次处于 `pending` / `running` 时发生，不会再把 `aborted` 翻成 `completed`。

### 3.5 动态回归计划

- `test_plan.selector`（可空 JSONB）：`{modules, priorities, case_types, include_issue_ids}`。从计划建轮次时，用例集合 = 手工加入的用例 ∪ 满足规则的 `active` 用例（去重，按手工顺序在前、其余按用例号）。autopilot 的 `test_run` 模式走同一条路径，新用例自动进入夜间回归。
- 计划详情页显示规则与“当前会纳入 N 条”。

### 3.6 本次不做，记为提案

- **B3 `case_type` 拆维度**（层级 × 技法 × 质量属性）：牵涉筛选、生成、契约与历史数据迁移。3.1 / 3.2 把覆盖的观察口径从 `case_type` 移到了测试点与其类别上，B3 的危害随之大幅下降；保留为提案 TS-041，待验收后决定。
- **结果与构建绑定的“过期”判定**（A2 的完整解）：测试点 3.1 已经让“需求改了之后补点”成为显式动作；按 `build_ref` 判定通过是否过期需要先统一构建号来源（目前是自由文本），记为提案 TS-042。
