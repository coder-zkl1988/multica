# 问题排查与转项目设计

日期：2026-08-24
状态：已确认，待实施

## 1. 背景

团队当前主要在飞书群中描述问题、@ Agent 并调用 `sy-ai-workflow` 的
`sy-issue-diagnose` 能力联合检查代码、日志和数据。排查过程和结论散落在聊天中，
无法稳定沉淀环境、证据、执行状态、项目交接和质量反馈。

Multica 已有 Agent Task、评论、附件、通知、项目资源和 worktree 执行能力，但
Issue 表达的是已经明确的实施任务。问题排查在根因确认前可能没有代码改动，也可能
最终属于配置、数据或操作问题，因此不能用 Issue 代替。

## 2. 目标与非目标

### 2.1 目标

- 新增独立于 Issue 的“问题排查”对象和工作区入口。
- 成员用文字和图片描述测试或线上问题并指派一个 Agent。
- 创建后自动调用内部诊断能力，保留进度、追问、证据和结构化结论。
- 由人确认结论后关联已有项目或新建一个需求型修复项目。
- 在确认结论和转项目两个节点收集轻量质量反馈。
- 向工作区所有者和管理员提供问题排查统计。
- 项目开发必须在从仓库默认主干创建的新 worktree 分支中执行。

### 2.2 非目标

- 不接收或同步飞书消息；首版只支持 Multica 内手工输入文字和粘贴图片。
- 不新增飞书式聊天室，不复刻 Issue 数据模型。
- 不在确认结论前修改代码或自动创建项目。
- 不在转项目时自动创建实施 Issue 或立即启动开发。
- 不把 Project 解释为一个 Git 仓库；Project 仍表示一次需求或交付，可关联多个资源。
- 不提供跨工作区的平台级统计后台。
- 不向用户暴露 `sy-ai-workflow`、`sy-issue-diagnose`、skill 挂载或内部路由名称。

## 3. 产品模型

### 3.1 Investigation

新增 `Investigation`，中文名称为“问题排查”。它是工作区级业务对象，至少保存：

- 标题、问题描述、创建人和创建时间；
- 环境：`test` 或 `production`；
- 指派 Agent；
- 状态；
- 当前 Agent Task 和历史运行；
- 结论：根因、证据、置信度、问题分类、修改建议和未确认事项；
- 关联项目；
- 创建时实际使用的诊断能力及版本快照，仅供内部审计和管理员统计；
- 首次开始、等待补充、结论提交、人工确认和转项目时间。

状态只有四个：

1. `investigating`：排查中；
2. `needs_input`：待补充；
3. `awaiting_confirmation`：结论待确认；
4. `completed`：已完成。

Agent 运行失败、离线、阻塞和重试属于运行状态，不增加业务状态。是否已关联项目也是
独立关系，不增加“已转项目”状态。

### 3.2 评论与附件

所有工作区成员都能查看、评论和补充图片。评论时间线展示成员回复、Agent 进度、
补充信息请求、结构化结论、确认和转项目系统事件。

排查单保持独立，不创建隐藏 Issue。实现上复用现有编辑器、附件上传、评论展示、
实时事件和通知组件；持久层使用排查单自己的评论归属，避免把现有 Issue 评论查询全部
改成通用多态资源模型。首版不抽象“任意资源评论框架”。

### 3.3 Agent Task

现有 Agent Task 继续作为唯一执行队列。任务增加可选的 `investigation_id` 归属，
并保证 Issue Task 与 Investigation Task 二选一。排查任务复用现有排队、领取、运行、
流式消息、失败、取消、重试、会话续接和用量记录。

排查任务由服务端生成受控执行上下文，固定包含：

- 排查单 ID、环境、问题描述和附件；
- 后续成员补充信息；
- 内部诊断能力标识和版本快照；
- 线上只读与测试环境写入二次确认规则；
- 结构化进度事件和最终结论契约。

用户只选择 Agent。服务端校验 Agent 当前可运行该能力，并在任务上下文中强制调用
`sy-issue-diagnose`。页面只显示“自动排查”。能力不可用时显示“该 Agent 当前无法执行
问题排查”，不暴露内部 skill 名称。

## 4. 用户流程

### 4.1 创建与自动排查

工作区主导航新增“问题排查”。列表支持按状态、环境、Agent 和更新时间筛选。

创建表单必填：

- 环境：测试或线上；
- 问题描述；
- 排查 Agent。

图片可选且支持多张。事故时间、业务 ID、页面地址、日志关键词等首版不做独立必填
字段，用户可写入描述。创建成功后立即排队，不再要求点击“开始排查”。

环境在任务启动后锁定。需要切换环境时，用户必须明确重启排查，旧任务和证据保留。

### 4.2 待补充

当关键事实不足时，Agent 发出补充信息请求并把状态置为 `needs_input`。成员评论或补图
后，系统将新增内容送入同一排查上下文并恢复 `investigating`。重复提交和网络重试不能
创建多个并行任务。

### 4.3 结论确认

Agent 只能提交结论并进入 `awaiting_confirmation`，不能自行确认或创建项目。结论必须
包含：

- 核心判断和因果链；
- 三角证据及来源、时间或代码 SHA；
- `confirmed`、`provisional` 或 `unverified` 置信度；
- 短期处理、长期修改建议和仍待确认问题。

排查单创建人、工作区所有者和管理员可以确认。其他成员可以继续评论和补充，但不能
确认或转项目。确认后进入 `completed`。无需修复的问题也在确认后完成。

### 4.4 关联或新建项目

确认结论后显示两个动作：

- 关联已有项目；
- 新建修复项目。

排查单永久保留，并与项目双向关联。重复操作必须返回现有关系，不能重复创建项目。

新项目按“一次需求/一次交付”创建，自动带入：

- 排查单标题；
- 环境；
- 原始问题描述和图片引用；
- 已确认根因、证据、置信度和修改建议；
- 原排查单链接；
- 开发约束。

负责人、项目资源、仓库和计划时间由用户在确认界面选择，不沿用排查 Agent。转项目
只建立交付上下文，不创建实施 Issue，也不启动 Agent。

项目描述固定加入：

```text
开发约束
- 必须使用独立 Git worktree。
- 必须从仓库默认主干创建新分支。
- 禁止直接修改主工作区或主干分支。
```

描述用于人和 Agent 阅读，但不是唯一约束。正式启动开发前，平台还必须校验项目已关联
仓库、执行模式为 `worktree`、默认主干可解析并记录基线 SHA。任务从该基线创建新分支；
任一条件不满足时拒绝启动。转项目本身不提前创建 worktree 或分支。

## 5. 环境与安全

### 5.1 线上环境

线上排查始终只读。代码、日志和数据库证据遵守 `sy-issue-diagnose` 的读取、脱敏、
行数预算和跨角印证规则。任何产品代码修改、数据库写入或部署都不属于排查任务权限。

### 5.2 测试环境

测试环境允许诊断能力提出受控数据写入，但每条写入仍必须执行预览、影响行数检查、
精确语句二次确认、事务执行和结果复核。用户创建排查单或选择测试环境不构成写入授权。

### 5.3 内容信任边界

问题描述、评论、图片 OCR、日志和数据库内容都属于不可信输入，只能作为诊断证据，
不能覆盖系统指令、调用额外能力或扩大权限。

## 6. 轻量反馈

反馈在两个独立检查点采集：

1. `diagnosis_confirmed`：确认排查结论后，评价诊断质量；
2. `project_converted`：关联或新建项目后，评价平台交接体验。

每个检查点一屏完成：

- 第一步只选择 1 至 5 分；
- 仅 1 至 3 分时展开可选归因：诊断能力、平台体验、两者都有、不确定；
- 评论始终可选；
- 可跳过，之后可补评或修改；
- 同一用户、排查单、检查点只有一条可编辑反馈，不重复弹出。

服务端同时记录被评价的 Agent、Task、诊断能力版本、环境、任务状态、失败原因、重试数、
耗时和应用版本。用户归因表示主观感受，不能替代客观故障分类。

## 7. 管理员统计

现有“统计”页面新增“问题排查”子 Tab。入口和 API 仅允许当前工作区所有者和管理员；
成员不可见，服务端必须鉴权，不能只在前端隐藏。

首版指标：

- 创建数、开始排查数、确认完成数和转项目数；
- 完成率和转项目率；
- 首次开始时间、结论确认时间和转项目时间；
- Agent 失败、离线阻塞和重试比例；
- 两个反馈检查点的参与率、平均分和评分分布；
- 低分归因分布；
- 按时间范围、环境、Agent 和诊断能力版本筛选；
- 从失败或低分记录下钻到当前工作区的具体排查单。

统计必须同时显示样本量和反馈参与率。小样本不做自动因果判断。原始评论默认不在面板
平铺，也不提供跨工作区搜索或导出。

## 8. 数据与 API 边界

新增最小持久对象：

- `investigation`：主体、状态、环境、Agent、结论、项目关系和里程碑时间；
- `investigation_comment`：排查单评论及线程关系；
- `investigation_feedback`：两个检查点的评分、评论、归因和运行快照；
- 现有 `agent_task_queue`、`attachment`、`inbox_item` 增加排查单归属所需字段。

新迁移使用 fork 保留的 800 以上编号，不新增外键或级联操作。关系校验和删除清理由服务
层显式执行；必须原子完成的创建、确认、关联和清理由应用事务保证。所有新增索引使用
单语句 `CREATE INDEX CONCURRENTLY` 或 `CREATE UNIQUE INDEX CONCURRENTLY` 迁移。

服务端至少提供：

- 创建、列表、详情和更新排查单；
- 新增评论和附件；
- 重试或更换 Agent；
- 提交与确认结论；
- 关联已有项目或原子创建项目并关联；
- 提交或修改反馈；
- 管理员统计。

确认结论、续跑、重试、转项目和反馈写入都必须幂等。客户端使用 TanStack Query 管理全部
服务端状态；Zustand 只保存筛选、草稿和弹窗等视图状态。WebSocket 事件更新或失效
Query 缓存，不把排查数据镜像到 Zustand。

## 9. 失败处理

- Agent 离线或能力不可用：排查单保留，运行显示可理解的失败原因，支持重试或换 Agent。
- 运行中断：保留 Task 和已产生证据，从同一排查单恢复，不创建第二个排查单。
- 待补充重复提交：合并到同一恢复动作，禁止并行重复运行。
- 新建项目失败：事务回滚项目关系，排查结论和状态不受影响。
- worktree、默认主干或基线解析失败：项目仍存在，但开发任务拒绝启动并展示修复条件。
- 统计聚合失败：不影响排查主流程；页面显示失败并允许重试。

## 10. 权限

| 操作 | 成员 | 创建人 | 管理员/所有者 | Agent |
| --- | --- | --- | --- | --- |
| 创建排查单 | 是 | 是 | 是 | 否 |
| 查看、评论、补图 | 是 | 是 | 是 | 仅任务上下文 |
| 重试或换 Agent | 否 | 是 | 是 | 否 |
| 确认结论 | 否 | 是 | 是 | 否 |
| 关联或新建项目 | 否 | 是 | 是 | 否 |
| 提交自己的反馈 | 是 | 是 | 是 | 否 |
| 查看排查统计 | 否 | 否，除非是管理员 | 是 | 否 |

新建和关联项目继续遵守现有项目权限；本表不扩大既有权限。

## 11. 验收标准

- 成员能用文字、图片、环境和 Agent 创建独立排查单，并自动开始排查。
- 用户界面不出现内部 workflow 或 skill 名称。
- 线上排查没有写入权限；测试写入需要精确二次确认。
- 进度、待补充、结论和历史运行在同一时间线可追溯。
- Agent 不能确认结论或创建项目。
- 创建人或管理员能确认结论，并幂等地关联或创建一个需求型项目。
- 新项目完整携带排查上下文和开发约束，原排查单仍可访问且双向关联。
- 正式开发只在从默认主干基线创建的独立 worktree 分支执行。
- 两个反馈检查点都可一击评分、可跳过、低分才展开归因，并允许之后修改。
- 所有者和管理员能在当前工作区统计页查看可靠指标，成员无法访问页面或 API。
- 失败、重试、重复点击和网络重放不会造成重复任务、项目或反馈。

## 12. 测试策略

- 服务层：状态机、权限、自动排队、待补充恢复、结论确认和环境锁定。
- 数据层：应用级关系校验、显式删除清理、事务回滚和幂等约束。
- Agent Task：排查归属、受控能力上下文、续跑、失败、重试和换 Agent。
- 安全：线上只读、测试写入确认、附件/日志不可信输入和服务端统计鉴权。
- 项目交接：关联已有项目、新建项目回滚、双向链接和描述内容。
- worktree：默认主干解析、固定基线 SHA、新分支创建以及失败闭锁。
- 前端：创建表单、时间线、权限按钮、低分渐进问卷和管理员 Tab。
- 实时事件：排查、评论、Task、项目关系和反馈更新的 Query 缓存一致性。

## 13. 延后项

- 飞书同步、链接抓取和外部消息导入；
- 多 Agent 同时作为主排查人；
- 自动创建实施 Issue；
- NPS、可配置问卷和自动责任判定；
- 跨工作区统计、原始评论搜索和导出；
- 把评论、任务或工作流抽象成面向任意业务对象的通用框架。
